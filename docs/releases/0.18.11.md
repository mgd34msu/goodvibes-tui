# 0.18.11

`0.18.11` fixes the version-boundary leak between the TUI product release and the SDK release line, and it closes the remaining TUI-side race around those versioned release surfaces.

The concrete issue was:

- the TUI checked in `docs/foundation-artifacts/operator-contract.json`
- that artifact was being exported through the raw SDK contract builder
- so the artifact carried the SDK package version instead of the TUI product version

That was the wrong boundary for a TUI-owned release artifact.

There was also still a TUI-side staging race:

- `prebuild` updated `src/version.ts` and `README.md`
- `foundation:artifacts` rewrote `docs/foundation-artifacts/*`
- `publish:package` staged those same files independently
- the release build job compiled fresh checkouts without forcing those surfaces back into sync first

That meant the TUI could still publish or compile from stale version-bearing files even after the SDK-side fallback fix landed.

## What Changed

### TUI Foundation Artifact Export Uses the TUI Contract Surface

The TUI export script now builds the checked-in operator contract artifact through the TUI’s own contract wrapper.

That means:

- the artifact still inherits the canonical contract shape from the SDK
- but the TUI-owned `product.version` field now reflects the TUI product version
- the checked-in artifact no longer drifts onto an SDK release number

### Release Gate Aligned to the Same Boundary

The foundation artifact release gate now validates against the TUI contract wrapper too.

That matters because the old gate was enforcing the wrong thing:

- it only checked whether the artifact matched the SDK builder output
- which allowed the SDK version to leak into the TUI-owned artifact without failing release validation

Now the gate enforces the actual intended product boundary.

### Release Surfaces Are Now Synchronized Under One Lock

The TUI now uses one shared workspace lock for the files that define release-visible version state:

- `src/version.ts`
- `README.md`
- `docs/foundation-artifacts/*`
- `src/types/generated/foundation-client-types.ts`

`prebuild` now synchronizes all of those surfaces together instead of only rewriting the local fallback version.

`publish:package` now runs the same sync before it stages a tarball, so a package publish cannot race a version or artifact rewrite and capture an inconsistent mix of files.

The release build job now does the same thing before compiling binaries on a fresh checkout, so the release assets and the published npm package are built from the same synchronized product surface.

### SDK Updated to `0.18.26`

This release also moves the TUI to `@pellux/goodvibes-sdk@0.18.26`.

That SDK patch fixes two downstream problems:

- the baked SDK runtime version fallback now stays aligned with the SDK package version instead of carrying an old hardcoded literal
- the SDK build/stage path now uses a shared workspace lock, which closes the recurring `dist` race between `validate` and `release:dry-run`

For the TUI, that means rebuilt binaries stop carrying the stale embedded SDK fallback string from `0.18.14`.

Combined with the TUI-side surface sync, that means the compiled app header, the checked-in foundation artifact, the published tarball, and the release binaries all move together on the TUI product version instead of drifting independently.
