# GoodVibes TUI `0.18.6`

Superseded packaging correction release for GoodVibes TUI.

This package shape fixed the registry-size problem, but the tagged release still failed before publish because source-checkout `bun install` ran the binary-download `postinstall` path. The successful public release shipped in `0.18.7`.

`0.18.4` established the canonical SDK cutover. `0.18.5` attempted to ship the public package with all platform binaries bundled into a single tarball, but that distribution was too large for both npmjs and GitHub Packages. `0.18.6` fixes the delivery model itself so the TUI can be published and installed cleanly.

## Package Identity

- npmjs package: `@pellux/goodvibes-tui`
- GitHub Packages mirror: `@mgd34msu/goodvibes-tui`
- installed commands:
  - `goodvibes`
  - `goodvibes-daemon`

The package identity is scoped. The installed command names stay unscoped and product-oriented.

## What Changed

### Correct npm install behavior

The npm package no longer tries to carry every release binary for every supported platform.

Instead, `postinstall` now:

- detects the current supported platform
- installs the matching TUI binary
- installs the matching standalone daemon binary
- stores those binaries in the installed package
- leaves `goodvibes` and `goodvibes-daemon` on the user path through the package `bin` entries

This keeps the install experience simple while making the package small enough for both registries.

### Release ordering is now correct

The release workflow now creates the GitHub Release and uploads the binary assets before it publishes the npm packages.

That matters because the package installer now resolves binaries from the version-matched GitHub Release:

- the release assets exist before registry users can install the package
- npmjs and GitHub Packages both publish the same small package shape
- the package no longer depends on a follow-up manual asset upload to become usable

### Install smoke now tests the real path

The workflow no longer tests a tarball that already contains vendored binaries.

It now tests the actual intended install path:

- pack the npm tarball
- install it in a clean temp project
- run `postinstall`
- confirm that both `goodvibes` and `goodvibes-daemon` are installed and executable
- confirm that the current platform’s TUI and daemon binaries are present after install

### Publish guards were tightened

The package validation now fails if:

- vendored binaries slip back into the published tarball
- the tarball grows past the publish-size guardrail
- either launcher bin is missing or non-executable
- required runtime/bootstrap files are missing

## Summary

`0.18.6` is the first TUI release where the public package model, release asset model, release notes, and registry publishing model all line up:

- canonical SDK cutover already in place
- scoped npm and GitHub Packages identities
- two installed CLI commands
- package small enough to publish
- GitHub release assets available before publish
- real postinstall-based binary install for both the TUI and the standalone daemon
