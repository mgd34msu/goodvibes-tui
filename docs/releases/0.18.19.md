# 0.18.19: Review-feedback follow-up for 0.18.18 render perf

**Released**: 2026-04-16
**Type**: Patch (test + docs + error-handling tightening)

## Summary

The 0.18.18 review scored 9.76/10, identifying three sub-10 dimensions. With the runtime WRFC score threshold now set to 10.0, this release lifts each dimension back to perfect.

## What changed

### Error Handling: render coalescer wraps both render paths in try/catch

`src/runtime/bootstrap-core.ts`: the `setImmediate` scheduler callback and the throttled `setTimeout` callback now each guard `renderRequestRef.value()` with try/catch. A thrown render exception no longer wedges the scheduler. Specifically:

- `renderScheduled = false` runs BEFORE the render attempt, guaranteeing the next `requestRender()` call can schedule regardless of render outcome
- Render errors are logged at `logger.error` level with context
- Both the immediate and throttled branches are protected symmetrically

Before this change, a single render exception thrown from within the `setImmediate` callback could leave `renderScheduled = true` permanently, deadlocking the TUI until restart.

### Testing

`src/test/renderer/render-perf.test.ts` gains two new tests:

1. **R1 16ms throttle branch**: simulates two bursts landing within the 16ms window using a monotonic clock, asserting the second render is delayed via `setTimeout` rather than fired immediately. The previous suite only covered the `setImmediate` immediate branch.

2. **R3 Compositor buffer identity**: drives a real `Compositor` instance through 10 frames at identical dimensions and asserts the observed set of `frontBuffer`/`backBuffer` instances has cardinality exactly 2. Filters the brief post-swap null so it doesn't inflate the count. Proves the 0.18.18 R3 promise ("2 buffer instances per session, not per frame") that the review flagged as untested.

Suite now has 11 tests in `render-perf.test.ts` (up from 10); total across the project is 438/438 passing.

### Maintainability: mid-render invalidation hazard documented

`src/renderer/panel-composite.ts`: added a JSDoc block above the `renderPanel` cache explaining the race where:

1. A panel's `render()` is called
2. An event listener fires MID-RENDER and sets `needsRender = true`
3. The trailing `markRendered()` clobbers that back to `false`
4. Next frame serves stale cached output

The doc includes (a) why this is rare in practice (render is synchronous, runtime-bus listeners typically run outside the render pass), (b) a workaround for panels that intentionally mutate during render (call `this.invalidate()` AFTER the trailing work), and (c) a deferred fix proposal (snapshot `needsRender` before `render()` and only clear if the snapshot was true).

This preserves the simpler implementation today while giving future contributors the context to fix it correctly if the hazard ever manifests.
