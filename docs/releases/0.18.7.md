# GoodVibes TUI `0.18.7`

First successful public registry release for GoodVibes TUI after fixing both the package size problem and the repo-checkout install path.

`0.18.6` corrected the public package model, but the release workflow still failed before publish because the repo checkout ran `postinstall` during `bun install` and tried to download release binaries before the GitHub Release existed. `0.18.7` fixes that last blocker.

## What Changed

### Source checkouts no longer trigger release-binary downloads

The TUI package install script now distinguishes between:

- a source checkout of the repository
- an installed published package

In a source checkout, `postinstall` now skips the release-binary download path. That means:

- local development installs do not fail waiting for release assets
- CI validation jobs can install dependencies before the release is created
- the release workflow can validate, build, create the GitHub Release, and only then publish the npm packages

### Published installs still fetch the right binaries

The public install behavior remains the same:

- package names:
  - npmjs: `@pellux/goodvibes-tui`
  - GitHub Packages: `@mgd34msu/goodvibes-tui`
- installed commands:
  - `goodvibes`
  - `goodvibes-daemon`
- install behavior:
  - the published package downloads the matching TUI and standalone daemon binaries for the current platform during `postinstall`

### Release ordering remains aligned with package install behavior

The release workflow still:

- validates the repo
- builds the TUI and daemon binaries
- smoke-tests the packed npm tarball through the real `postinstall` path
- creates the GitHub Release with binary assets
- publishes npmjs and GitHub Packages packages only after those assets exist

That keeps the package install path and the release asset path consistent.

- `bun run publish:dry-run:github`
- local package install smoke through `postinstall` with staged release artifacts
- `git diff --check`

## Summary

`0.18.7` is the first release where the full TUI public delivery path is coherent end to end:

- canonical SDK cutover already in place
- correct scoped package identities
- both `goodvibes` and `goodvibes-daemon` on the installed CLI surface
- package small enough to publish
- release assets created before registry publish
- source checkouts no longer trip the release-binary install path
- published installs still fetch the version-matched binaries they need
